## 1. 수집 전 상태 확인

```bash
ops@vm$ ps -o user,pid,etime,cmd -C agent-app-linux     # 앱 실행 중 (agent-admin)
ops@vm$ sudo crontab -u agent-admin -l | grep monitor    # cron 등록
ops@vm$ sudo tail -n 3 /var/log/agent-app/monitor.log    # 최근 1~2분 내 기록
ops@vm$ sudo ufw status | head -n 1                      # Status: active (06장 T4 후 다시 켰는지!)
```

## 2. 내가 작성한 스크립트를 저장소에 반영

```bash
ops@vm$ for f in monitor.sh report.sh log_retention.sh; do
          sudo test -f $AH/bin/$f && sudo cp $AH/bin/$f $REPO/scripts/$f
        done
ops@vm$ sudo chown ops: $REPO/scripts/*.sh
ops@vm$ sudo diff $AH/bin/monitor.sh $REPO/scripts/monitor.sh && echo "IDENTICAL"
ops@vm$ bash -n $REPO/scripts/monitor.sh && echo "SYNTAX OK"
```

## 3. 증거 자동 수집

```bash
ops@vm$ cd $REPO
ops@vm$ sudo ./scripts/collect_evidence.sh          # cron 확인을 위해 약 70초 대기
ops@vm$ ls -l submission/evidence/
```

| 생성 파일 | 미션 필수 증거 체크리스트 |
|---|---|
| `00_system.txt` | (환경 정보) |
| `01_ssh.txt` | SSH 포트 변경(20022) 및 Root 원격 접속 차단 설정 확인 |
| `02_firewall.txt` | 방화벽(UFW) 활성화 및 20022/tcp, 15034/tcp 만 허용 |
| `03_accounts.txt` | 계정/그룹(agent-admin/dev/test, agent-common/core) 생성 확인 |
| `04_dirs_acl.txt` | 디렉토리 구조 및 권한(ACL 포함) 확인 + 권한 테스트 PASS/FAIL |
| `05_env_app.txt` + **`05_app_boot.txt`**(05장에서 직접 저장) | 앱 Boot Sequence 5단계 [OK] 및 "Agent READY" |
| `06_monitor_run.txt` | monitor.sh 실행 결과(프로세스/포트/리소스/경고) |
| `07_monitor_log.txt` | /var/log/agent-app/monitor.log 누적 기록(최근 라인) |
| `08_cron.txt` | crontab 매분 실행 등록 및 자동 실행 확인(1분 후 로그 증가) |
| `09_bonus.txt` | (보너스) |

수집이 끝나면 `[CHECK] 실패 항목 있음` 줄이 없어야 합니다. 있으면 해당 파일에서 `<<< FAIL` 을 찾아 원인을 고친 뒤 다시 수집합니다.

```bash
ops@vm$ grep -n 'FAIL\|exit=[1-9]' submission/evidence/*.txt
# 06장 T3 처럼 "일부러" 실패시킨 것이 아니라면 없어야 함
ops@vm$ grep -n 'increase\|증가량' submission/evidence/08_cron.txt    # 증가량 1 이상
```

## 7. 최종 체크리스트 & 자기 점검

### 7-1. 기능 요구사항

- [ ] SSH 20022, `PermitRootLogin no`, 22번 LISTEN 없음 — `01_ssh.txt`
- [ ] UFW active, `deny (incoming)`, ALLOW 는 20022/tcp · 15034/tcp (v6 포함)뿐 — `02_firewall.txt`
- [ ] agent-admin/dev/test, agent-common(3명), agent-core(admin, dev) — `03_accounts.txt`
- [ ] upload_files(agent-common RW), api_keys·/var/log/agent-app(agent-core ONLY RW), ACL — `04_dirs_acl.txt` 모두 PASS
- [ ] AGENT_* 5개, 키 파일, 일반 계정 실행, 5단계 [OK], Agent READY, 0.0.0.0:15034 — `05_*.txt`
- [ ] monitor.sh: `agent-dev:agent-core 750`, Health Check exit 1, 방화벽 경고, CPU/MEM/DISK, 임계값 경고, 로그 형식, 10MB×10 — `06_*.txt`, `07_*.txt`
- [ ] agent-admin crontab 매분, 자동 증가 확인 — `08_cron.txt`
- [ ] 스크립트는 Bash 로만 작성, 필요한 경우에만 sudo 사용
- [ ] (보너스) report.sh / log_retention.sh — `09_bonus.txt`

### 7-2. 과제 목표 — 스스로 설명하기

각 질문에 **자기 말로 3~5문장** 답할 수 있어야 합니다. 먼저 답해 보고, 아래 "핵심 포인트"와 비교하세요.

<details>
<summary><b>① SSH 포트 변경과 Root 원격 접속 차단이 왜 기본 보안인가?</b></summary>

- 포트 변경: 22번을 노리는 **자동화 공격 소음 감소**, 로그 가독성 향상. 단, 스캔하면 드러나므로 **단독으로는 보안이 아님**(은폐) → 방화벽·키 인증과 겹쳐야 의미.
- root 차단: 이름이 알려진 **최고 권한 계정**에 대한 무차별 대입 차단, 개인 계정 + sudo 로 **책임 추적성** 확보.
- 검증: `sshd -T`(유효 설정), `ss -tulnp`(실제 LISTEN), 실제 접속 시도.
</details>

<details>
<summary><b>② "필요 포트만 허용" 방화벽 정책을 어떻게 구성·검증하는가?</b></summary>

- `default deny incoming` + 필요한 포트만 `allow 포트/tcp` (화이트리스트). stateful 이라 나가는 연결의 응답은 자동 허용.
- 검증은 두 층: ① 설정(`ufw status verbose`, v6 포함) ② **외부 실측**(`nc -vz`: 허용+LISTEN=성공, 허용+미LISTEN=refused, 차단=timeout).
- LISTEN 포트 ≠ 허용 포트 → 심층 방어. Docker 등 UFW 우회 사례 때문에 실측이 필요.
</details>

<details>
<summary><b>③ 역할 기반 계정/그룹과 ACL로 공유/보안 디렉토리를 분리하는 이유는?</b></summary>

- 데이터 민감도가 다르면 권한 경계를 나눈다: 업로드(협업 전원) vs 키·로그(핵심 인원). **최소 권한** → 유출·변조 반경 축소.
- 권한은 **그룹**에 주고 사람은 그룹에 넣어 관리 비용 최소화.
- setgid(그룹 상속) + default ACL(umask 무관 그룹 RW) 로 공유가 "깨지지 않게", 홈 디렉토리 통과는 ACL `--x` 로 **필요한 그룹에만 최소 권한**.
</details>

<details>
<summary><b>④ 환경 변수로 실행 환경을 고정하는 이유와 검증 방법은?</b></summary>

- 코드와 설정 분리 → 같은 바이너리를 여러 로봇/환경에 배포, 비밀 값의 **위치**만 주입.
- 실행 경로(로그인 셸/cron/systemd)마다 환경이 달라지는 문제 → **단일 환경 파일**을 모두가 읽게 고정. 파일은 root 소유로 변조 방지.
- 검증: 로그인 셸 `env`, cron 재현 `env -i`, **실행 중 프로세스의 실제 값 `/proc/<PID>/environ`**. 환경 변수는 시작 시 복사되므로 변경 후 재시작 필요.
</details>

<details>
<summary><b>⑤ 쉘 스크립트로 상태를 수집·기록해 운영 문제를 추적하는 흐름은?</b></summary>

- Health Check(프로세스·포트, 실패 시 exit 1) → 상태 점검(방화벽, 경고) → Metric 수집(/proc/stat 차분, MemAvailable, df) → 임계값 경고 → **정형화된 한 줄 로그** 기록.
- 종료 코드로 자동화 도구와 소통, 경고는 수집을 멈추지 않음(장애 순간 데이터가 가장 중요).
- 로그 형식(`[시각] 키:값`) 덕분에 시간대별 추적·통계(report.sh)가 가능 → "감"이 아닌 데이터로 원인 분석.
</details>

<details>
<summary><b>⑥ crontab 으로 주기 실행하고, 로그 보존 정책이 왜 필요한가?</b></summary>

- cron 은 사람 없이 **일정한 간격의 기록**을 보장. cron 은 최소 환경(PATH, 환경 변수 없음)이므로 스크립트가 스스로 환경을 설정하고, 출력은 logger 로 journald 에.
- 매분 기록은 계속 쌓임 → **크기 회전**(파일 폭주 방지), **압축**(공간 절약), **삭제**(보존 기간 정책, 불필요한 데이터 최소 보유). 디스크가 차면 서비스 전체가 멈춘다(로봇은 특히 저장공간·플래시 수명 제한).
</details>
