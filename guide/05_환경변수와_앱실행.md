# 05. 환경 변수와 앱 실행 — Boot Sequence 5단계 [OK]

## 이 장의 목표

| 미션 요구사항 | 확인 방법 |
|---|---|
| 환경 변수 `AGENT_HOME`, `AGENT_PORT`, `AGENT_UPLOAD_DIR`, `AGENT_KEY_PATH`, `AGENT_LOG_DIR` 설정 | `env`, `/proc/<PID>/environ` |
| 키 파일 생성 (내용 `agent_api_key_test` 1줄) | `ls -l`, `wc -l` |
| **일반 계정**으로 앱 실행 (root 금지) | `ps -o user` |
| Boot Sequence 5단계 모두 `[OK]` + `Agent READY` | 부팅 출력 기록 |
| `0.0.0.0:15034` LISTEN | `ss -tlnp` |

그리고 다음을 **설명할 수 있어야** 합니다.
> 환경 변수(AGENT_HOME 등)로 실행 환경을 고정하는 이유와 검증 방법은?

---

## 1. 개념

### 1-1. 환경 변수는 "프로세스의 속성"이다

```
 bash (AGENT_HOME=/home/...)                 ← export 된 변수는
   └─ fork+exec ─▶ agent-app (AGENT_HOME 복사본)   자식 프로세스에 "복사"된다
```

- 환경 변수는 프로세스가 **시작될 때 부모로부터 복사**됩니다. 이후 부모에서 값을 바꿔도 이미 실행 중인 자식은 **옛 값을 그대로** 가집니다.
- `VAR=값` 은 셸 변수(자식에게 안 넘어감), `export VAR=값` 은 환경 변수(자식에게 넘어감).
- 그래서 **"지금 실행 중인 앱이 실제로 어떤 값을 받았는지"** 는 셸의 `echo` 가 아니라 `/proc/<PID>/environ` 으로 확인해야 합니다.

### 1-2. 왜 설정을 환경 변수로 주입하나

| 하드코딩 | 환경 변수 주입 |
|---|---|
| 경로·포트가 코드에 박혀 있음 | 코드는 같고 **실행 환경만** 다름 |
| 로봇마다 다른 설정 → 로봇마다 다른 빌드 | **하나의 바이너리**를 모든 로봇에 배포 |
| 키가 코드에 섞여 저장소로 유출 위험 | 키 **위치**만 알려주고 키는 코드 밖에 |

이것이 [12-Factor App](https://12factor.net/ko/config)의 "설정은 환경에 저장" 원칙입니다. 동시에 **"환경을 고정"** 해야 하는 이유도 있습니다. 누가 어떤 셸로 실행하느냐에 따라 값이 달라지면, "제 셸에서는 되는데요?" 류의 장애가 생깁니다. 그래서 값을 **한 파일에 정의하고 모든 실행 경로가 그 파일을 읽게** 만듭니다.

### 1-3. 환경 변수를 영구 설정하는 위치

| 위치 | 적용 대상 | 이 가이드 |
|---|---|---|
| `~/.bashrc` | 그 사용자의 대화형 bash | ❌ 사용자마다 따로 관리해야 함 |
| `/etc/environment` | 모든 사용자 (PAM) | ❌ 변수 참조 불가, 모든 사용자에게 노출 |
| `/etc/profile.d/*.sh` | 모든 **로그인 셸** | ✅ 로그인 시 공용 파일을 읽어오는 역할 |
| **`/etc/agent-app/agent.env`** | 이 파일을 읽는 모든 것 | ✅ **단일 진실 공급원** |
| systemd `EnvironmentFile=` | 서비스 | (현업 확장, [F3](field/F3_서비스운영_systemd_로그_시크릿.md)) |

```
               /etc/agent-app/agent.env   (root:agent-common 640)
                  │            │                 │
   /etc/profile.d/agent-app.sh │           systemd EnvironmentFile
   (로그인 셸: sudo -iu, ssh)   │           (현업: 서비스 실행)
                        monitor.sh 가 직접 source
                        (cron 은 로그인 셸이 아님!)
```

> **로그인 셸 vs 비로그인 셸**: `sudo -iu 사용자`, `ssh` 접속은 로그인 셸이라 `/etc/profile.d` 를 읽습니다. `sudo -u 사용자 명령`, **cron** 은 로그인 셸이 아니라서 읽지 않습니다. 06장 monitor.sh 가 환경 파일을 직접 읽는 이유입니다.

## 2. 실습

### 2-1. 환경 파일 설치

```bash
# 설정 디렉토리: root 소유, agent-common 은 읽기만
ops@vm$ sudo mkdir -p /etc/agent-app
ops@vm$ sudo chown root:agent-common /etc/agent-app
ops@vm$ sudo chmod 750 /etc/agent-app

ops@vm$ sudo install -m 640 -o root -g agent-common \
          $REPO/config/env/agent.env /etc/agent-app/agent.env
ops@vm$ sudo install -m 644 -o root -g root \
          $REPO/config/env/agent-app-profile.sh /etc/profile.d/agent-app.sh

ops@vm$ sudo cat /etc/agent-app/agent.env
```

내용(요약):

```
AGENT_HOME=/home/agent-admin/agent-app
AGENT_PORT=15034
AGENT_UPLOAD_DIR=/home/agent-admin/agent-app/upload_files
AGENT_LOG_DIR=/var/log/agent-app
AGENT_KEY_PATH=/home/agent-admin/agent-app/api_keys/t_secret.key   ← 미션 명세 값
```

> **왜 root 소유 + 그룹 읽기 전용인가?** `agent-dev` 가 이 파일을 고칠 수 있다면 `AGENT_LOG_DIR` 을 다른 곳으로 돌려 **로그를 숨기거나**, `AGENT_KEY_PATH` 를 바꿔 **다른 키를 읽게** 만들 수 있습니다. 실행 환경의 정의는 실행하는 사람이 바꿀 수 없어야 합니다.
>
> **왜 `$AGENT_HOME/upload_files` 가 아니라 전체 경로로 적었나?** systemd `EnvironmentFile` 은 `$변수` 참조를 펼치지 않습니다. 같은 파일을 셸과 systemd 가 모두 읽게 하려면 절대 경로로 적어야 합니다.

### 2-2. 환경 변수 로드 확인

```bash
ops@vm$ sudo -iu agent-admin
agent-admin@vm$ env | grep '^AGENT_' | sort
# AGENT_HOME=/home/agent-admin/agent-app
# AGENT_KEY_PATH=/home/agent-admin/agent-app/api_keys/t_secret.key
# AGENT_LOG_DIR=/var/log/agent-app
# AGENT_PORT=15034
# AGENT_UPLOAD_DIR=/home/agent-admin/agent-app/upload_files
agent-admin@vm$ exit

# 비교: 비로그인 셸은 profile.d 를 읽지 않는다
ops@vm$ sudo -u agent-admin bash -c 'echo "AGENT_HOME=[$AGENT_HOME]"'
# AGENT_HOME=[]
```

✅ 체크포인트: 로그인 셸에서는 5개가 모두 보이고, 비로그인 셸에서는 비어 있다. (이 차이를 이해하는 것이 07장 cron 디버깅의 핵심)

### 2-3. 키 파일 생성

```bash
ops@vm$ sudo -iu agent-admin
agent-admin@vm$ printf '%s\n' 'agent_api_key_test' > "$AGENT_HOME/api_keys/t_secret.key"
agent-admin@vm$ ls -l "$AGENT_HOME/api_keys/"
# -rw-rw---- 1 agent-admin agent-core 19 ... t_secret.key     ← default ACL 로 그룹 rw, other 없음
agent-admin@vm$ wc -l "$AGENT_HOME/api_keys/t_secret.key"      # 1
agent-admin@vm$ cat -A "$AGENT_HOME/api_keys/t_secret.key"     # agent_api_key_test$   (^M 이 없어야 함)
agent-admin@vm$ exit
```

> `echo` 대신 `printf '%s\n'` 을 쓰는 이유: `echo` 는 셸마다 `-e`, `\n` 처리 방식이 달라 결과가 흔들립니다. 파일 내용을 정확히 통제할 때는 `printf` 가 안전합니다.

### 2-4. 앱 바이너리 배포

```bash
ops@vm$ echo $APP_BIN                        # 00장에서 설정: agent-app-linux-x86 또는 -arm64
ops@vm$ sudo install -o agent-admin -g agent-admin -m 750 \
          $REPO/agent-app/$APP_BIN /home/agent-admin/agent-app/
ops@vm$ sudo ls -l /home/agent-admin/agent-app/
```

### 2-5. (실험) root 로 실행하면?

```bash
ops@vm$ sudo /home/agent-admin/agent-app/$APP_BIN
# >>> Starting Agent Boot Sequence...
# [1/5] Checking User Account            [FAIL]
#    >>> Error: Running as 'root' is forbidden.
# ...
```

앱 스스로 root 실행을 거부합니다. **서비스는 필요한 최소 권한의 전용 계정으로 실행**해야 앱이 탈취되어도 시스템 전체가 넘어가지 않습니다.

### 2-6. 첫 실행 — 명세대로 설정한 상태

SSH 가 끊겨도 앱이 살아 있도록 **tmux** 안에서 실행합니다.

```bash
ops@vm$ tmux new -s agent                 # tmux 세션 생성 (ops 소유)
ops@vm$ sudo -iu agent-admin              # tmux 안에서 agent-admin 로그인 셸로 전환
agent-admin@vm$ cd "$AGENT_HOME"
agent-admin@vm$ ./agent-app-linux-*
```

> tmux 기본 조작: 세션에서 빠져나오기(앱은 계속 실행) `Ctrl+b` 다음 `d` / 다시 들어가기 `tmux attach -t agent`

결과는 바이너리에 따라 둘 중 하나입니다.

#### 케이스 A — 5단계 모두 [OK]

명세와 앱이 일치하는 버전입니다. 2-8 로 넘어갑니다.

#### 케이스 B — `[2/5]` 에서 `Key Path Mismatch` (x86 바이너리 분석 결과 이쪽)

```
[1/5] Checking User Account            [OK]
   ... Running as service user 'agent-admin' (uid=1001)
[2/5] Verifying Environment Variables  [FAIL]
   >>> Key Path Mismatch. Expected: /home/agent-admin/agent-app/api_keys
   ...
System Boot Failed. Process Terminated.
```

**에러 메시지가 답을 알려줍니다.** 이 앱은 `AGENT_KEY_PATH` 로 **파일이 아니라 키 디렉토리**를 기대합니다.

### 2-7. (케이스 B) 실패 메시지를 따라 고치기

```bash
# ① 환경 파일 수정 (ops 에서. tmux 밖의 다른 SSH 터미널 또는 Ctrl+b d 로 빠져나와서)
ops@vm$ sudo sed -i 's|^AGENT_KEY_PATH=.*|AGENT_KEY_PATH=/home/agent-admin/agent-app/api_keys|' \
          /etc/agent-app/agent.env
ops@vm$ sudo grep KEY_PATH /etc/agent-app/agent.env
```

```bash
# ② 환경 변수는 "프로세스 시작 시 복사"되므로, agent-admin 셸을 새로 열어야 새 값이 보인다
agent-admin@vm$ exit
ops@vm$ sudo -iu agent-admin
agent-admin@vm$ echo $AGENT_KEY_PATH          # .../api_keys
agent-admin@vm$ cd "$AGENT_HOME" && ./agent-app-linux-*
```

다시 실행하면 이번에는 `[3/5]` 에서 멈춥니다.

```
[3/5] Checking Required Files          [FAIL]
   >>> Missing File: secret.key
   >>>    (Expected location: /home/agent-admin/agent-app/api_keys/secret.key)
```

```bash
# ③ 앱이 요구하는 파일명으로 키 파일 생성 (내용 동일)
agent-admin@vm$ printf '%s\n' 'agent_api_key_test' > "$AGENT_HOME/api_keys/secret.key"
agent-admin@vm$ ./agent-app-linux-*
```

> 명세의 `t_secret.key` 는 제출 증거와의 호환을 위해 남겨 둡니다. 단, **현업이라면 사용하지 않는 비밀 파일은 즉시 삭제**합니다(시크릿 확산 방지).

📝 **이 과정 전체를 수행 내역서의 "명세 편차(Deviation)" 절에 기록합니다.** 현업에서는 이런 불일치를 발견하면 ① 실제 동작 기준으로 운영 설정을 맞추고 ② 근거(에러 메시지)를 남기고 ③ 벤더/개발팀에 문서 수정을 요청합니다.

#### 부팅 실패 메시지 전체 표 (x86 바이너리 분석 기반)

| 단계 | 메시지 | 원인 → 해결 |
|---|---|---|
| 1/5 | `Error: Running as 'root' is forbidden.` | root/sudo 로 실행 → `sudo -iu agent-admin` 후 실행 |
| 2/5 | `Critical Env 'AGENT_HOME' is missing.` | 환경 변수 미로드 → **로그인 셸**(`sudo -iu`)인지, 파일을 고친 뒤 재로그인했는지 확인 |
| 2/5 | `Port mismatch (Expected 15034, Got …)` / `Invalid port format` | `AGENT_PORT` 값 오류 |
| 2/5 | `Upload Path Mismatch. Expected: …` / `Directory not found: …` | `AGENT_UPLOAD_DIR` ≠ `$AGENT_HOME/upload_files`, 또는 디렉토리 없음 |
| 2/5 | `Key Path Mismatch. Expected: …` / `File not found: …` | `AGENT_KEY_PATH` 를 메시지의 Expected 값으로 |
| 3/5 | `Missing File: secret.key (Expected location: …)` | 키 파일명/위치 |
| 3/5 | `Permission Denied: Cannot read …` | 키 파일 권한 → 04장 ACL 확인 |
| 3/5 | `Invalid Content in … (Expected: 'agent_api_key_test', Found: '…')` | 파일 내용 오타, CRLF |
| 4/5 | `Port 15034 is already in use.` | 앱이 이미 실행 중 → `ps -C agent-app-linux` |
| 5/5 | `Log directory not found` / `Permission Denied: User '…' cannot write to …` | 04장 `/var/log/agent-app` 권한, 그룹 추가 후 재로그인 여부 |

### 2-8. 성공 확인 + 부팅 출력 증거 남기기

성공하면 다음과 비슷하게 출력됩니다.

```
>>> Starting Agent Boot Sequence...
[1/5] Checking User Account            [OK]
   ... Running as service user 'agent-admin' (uid=1001)
[2/5] Verifying Environment Variables  [OK]
   ... All required Envs correct
[3/5] Checking Required Files          [OK]
   ... Verified 'secret.key' with correct key string.
[4/5] Checking Port Availability       [OK]
   ... Port 15034 is available.
[5/5] Verifying Log Permission         [OK]
   ... Log directory is writable: /var/log/agent-app
------------------------------------------------------------
All Boot Checks Passed!
Agent READY
... [SafetyGuard] Process priority lowered (nice=10).
... Agent listening at port 15034
... === Agent Worker Started ===
```

`Ctrl+C` 로 한 번 종료해 보고(`Agent Shutdown. Releasing resources.` 확인), **증거용으로 `script` 명령과 함께 다시 실행**합니다. `script` 는 터미널에 보이는 모든 출력을 파일로 기록합니다.

```bash
agent-admin@vm$ script -q -f -c "./agent-app-linux-*" /tmp/05_app_boot.txt
# Agent READY 가 나오고 몇 줄 로그가 흐르면 그대로 둔다 (앱은 계속 실행 상태)
```

📸 스크린샷: 5단계 [OK] ~ Agent READY 화면.

`Ctrl+b d` 로 tmux 에서 빠져나와 증거 파일을 복사합니다.

```bash
ops@vm$ cp /tmp/05_app_boot.txt $REPO/submission/evidence/05_app_boot.txt
ops@vm$ head -n 20 $REPO/submission/evidence/05_app_boot.txt
```

> 이후 앱은 이 tmux 세션에서 **계속 실행 상태로 둡니다.** 06·07장의 monitor.sh 가 이 프로세스를 감시합니다. VM 을 재부팅했다면 `tmux new -s agent` → `sudo -iu agent-admin` → `cd $AGENT_HOME && ./agent-app-linux-*` 로 다시 띄웁니다.

### 2-9. 실행 상태 검증 (ops 터미널)

```bash
# ① 0.0.0.0:15034 LISTEN (다른 사용자의 프로세스 정보를 보려면 sudo)
ops@vm$ sudo ss -tlnp 'sport = :15034'
# State  Recv-Q Send-Q Local Address:Port  Peer Address:Port Process
# LISTEN 0      1      0.0.0.0:15034       0.0.0.0:*     users:(("agent-app-linux",pid=5012,fd=3))

# ② 누가, 몇 개의 프로세스로 실행 중인가
ops@vm$ ps -o user,pid,ppid,ni,etime,cmd -C agent-app-linux
# USER         PID    PPID  NI     ELAPSED CMD
# agent-a+    5010    4990   0       02:11 ./agent-app-linux-x86
# agent-a+    5012    5010  10       02:11 ./agent-app-linux-x86
```

- **프로세스가 2개인 이유**: 이 앱은 PyInstaller "onefile" 방식입니다. **부모**가 내장된 파이썬 런타임을 임시 디렉토리(`/tmp/_MEIxxxx`)에 풀고, **자식**이 실제 앱을 실행합니다. 포트를 연 것(①의 pid)은 자식입니다.
- **이름이 `agent-app-linux` 인 이유**: 리눅스 커널은 프로세스 이름(comm)을 **15자**로 자릅니다. `agent-app-linux-x86` → `agent-app-linux`. 06장 monitor.sh 에서 이 이름으로 찾습니다.
- **NI 10**: 앱이 스스로 우선순위를 낮췄습니다(`[SafetyGuard]` 로그). 로봇에서 부가 기능이 주행 제어 같은 핵심 프로세스의 CPU를 뺏지 않게 하는 관례입니다.

```bash
# ③ 실행 중인 앱이 "실제로 받은" 환경 변수 (셸 echo 가 아닌 진짜 값)
ops@vm$ sudo tr '\0' '\n' < /proc/$(pgrep -n -x agent-app-linux)/environ | grep '^AGENT_' | sort

# ④ 외부에서 앱 포트 접속 (02장에서 refused 였던 것이 이제 succeeded)
mac$ nc -vz -w 3 <VM_IP> 15034
```

✅ 체크포인트: ① `0.0.0.0:15034` LISTEN ② USER 가 agent-admin ③ AGENT_* 5개 ④ succeeded

### 2-10. 앱이 무엇을 하는지 관찰

```bash
ops@vm$ sudo tail -n 20 /var/log/agent-app/agent_app.log
# ... [INFO] [CPU] Occupy core for ...s (Level ...)
# ... [INFO] [Memory] Increasing... (+25 MB) Total: 100 MB
# ... >>> PEAK REACHED (Max Load). Switching to RAMP DOWN. ▼ <<<
ops@vm$ top -u agent-admin        # q 로 종료
```

이 앱은 **CPU와 메모리 부하를 주기적으로 올렸다 내리는 테스트용 에이전트**입니다. 06장에서 monitor.sh 가 CPU/MEM 경고를 실제로 잡아내는지 확인할 수 있는 환경이 만들어진 것입니다. 앱 로그(`agent_app.log`)는 앱이 스스로 1MB × 3개로 회전합니다.

## 🤖 현장 노트 — 로봇에서의 앱 실행과 비밀 값

1. **tmux 가 아니라 systemd** — 현장에서 사람이 tmux 로 앱을 띄워 두는 일은 없습니다. 재부팅·크래시 시 자동 재시작, 로그 수집, 샌드박스를 위해 systemd 서비스로 운영합니다. 저장소의 [`config/systemd/agent-app.service`](../config/systemd/agent-app.service) 와 [F3](field/F3_서비스운영_systemd_로그_시크릿.md) 참고. (미션 제출은 "Ctrl+C 로 종료"하는 포그라운드 실행 기준이므로 이 장의 방식을 그대로 씁니다.)
2. **비밀 값이 셸 히스토리에 남는다** — 2-3 에서 `printf '...' > 파일` 로 키를 넣었으므로 키 문자열이 `~/.bash_history` 에 남았습니다. 테스트 키라 괜찮지만, 실제 키는 `read -rs KEY; printf '%s\n' "$KEY" > 파일; unset KEY` 처럼 **화면·히스토리에 남기지 않고** 넣거나 배포 도구가 넣습니다.
3. **환경 변수 자체도 비밀일 수 있다** — 키 "값"을 환경 변수로 주면 `/proc/<PID>/environ`, 크래시 덤프, `ps e` 등으로 새어 나갈 수 있습니다. 이 앱처럼 **환경 변수에는 경로만, 비밀은 권한이 잠긴 파일에** 두는 설계가 더 안전합니다.
4. **설정 드리프트** — 누군가 로봇 한 대의 `agent.env` 를 손으로 고치면 그 로봇만 다르게 동작합니다. 현장에서는 설정 파일을 저장소에서 관리하고 배포 도구로만 바꾸며, 주기적으로 해시를 비교해 **드리프트를 탐지**합니다.
