# F2. 원격 접속과 네트워크 — 현장 로봇의 SSH·방화벽

> 01·02장을 끝낸 VM 에서 **실습 가능한 것(🧪)** 과 **개념으로 알아둘 것(📖)** 을 구분했습니다.
> 🧪 실습 전 VM 스냅샷을 찍고, VM 콘솔 창을 열어 두세요.

---

## 1. 🧪 공개키 인증만 허용하기

비밀번호는 추측·유출·재사용될 수 있습니다. 공개키 인증은 **개인키 파일을 가진 사람만** 들어올 수 있고, 무차별 대입이 사실상 불가능합니다. 현장 로봇 SSH 보안에서 **포트 변경보다 훨씬 중요한** 설정입니다.

```bash
# 1) 내 PC 에서 키 생성 (이미 있으면 생략). 개인키에는 반드시 암호(passphrase)를 건다
mac$ ssh-keygen -t ed25519 -C "ops@my-laptop"

# 2) 공개키를 VM 에 등록 (~/.ssh/authorized_keys 에 추가됨)
mac$ ssh-copy-id -p 20022 ops@<VM_IP>

# 3) 키로 접속되는지 먼저 확인 (비밀번호를 묻지 않아야 함)
mac$ ssh -p 20022 -o PreferredAuthentications=publickey ops@<VM_IP> 'echo KEY-LOGIN-OK'
```

**3)이 성공한 뒤에만** 비밀번호 로그인을 끕니다.

```bash
ops@vm$ sudo tee /etc/ssh/sshd_config.d/20-auth.conf >/dev/null <<'EOF'
PubkeyAuthentication yes
PasswordAuthentication no
KbdInteractiveAuthentication no
EOF
ops@vm$ sudo sshd -t && sudo sshd -T | grep -Ei '^(passwordauthentication|pubkeyauthentication) '
ops@vm$ sudo systemctl restart ssh
```

```bash
# 새 터미널에서 검증
mac$ ssh robot-01 'echo still-ok'                                      # 키 → 성공
mac$ ssh -p 20022 -o PubkeyAuthentication=no ops@<VM_IP>               # → Permission denied (publickey).
```

> 파일 이름이 `20-` 이라 클라우드 이미지의 `50-cloud-init.conf`(여기에 `PasswordAuthentication yes` 가 있는 경우가 많음)보다 **먼저** 읽혀 우리 값이 이깁니다(01장 first-match 규칙).

📖 **플릿 규모에서는** — 로봇 1,000대 × 엔지니어 30명의 `authorized_keys` 를 관리하는 것은 불가능합니다. 그래서 **SSH 인증서**(`ssh-keygen -s` 로 CA 가 서명, 유효기간 8시간 등)를 쓰거나, 접속을 중앙 게이트웨이(bastion)로만 허용하고 거기서 인증·기록합니다. 퇴사자 처리 = CA 가 더 이상 서명하지 않음.

## 2. 🧪 fail2ban — 반복 실패하는 IP 자동 차단

```bash
ops@vm$ sudo apt install -y fail2ban
ops@vm$ sudo tee /etc/fail2ban/jail.d/sshd-20022.local >/dev/null <<'EOF'
[sshd]
enabled  = true
port     = 20022
backend  = systemd
maxretry = 5
findtime = 10m
bantime  = 1h
# 자기 자신(관리 PC)을 차단하지 않도록. <MY_PC_IP> 를 실제 IP 로
ignoreip = 127.0.0.1/8 ::1 <MY_PC_IP>
EOF
ops@vm$ sudo systemctl enable --now fail2ban
ops@vm$ sudo fail2ban-client status sshd
```

> ⚠️ `ignoreip` 없이 테스트하다 자기 PC 가 차단되면 VM 콘솔에서 `sudo fail2ban-client set sshd unbanip <IP>`.

## 3. 📖 "들어오는 문"을 아예 없애기 — 아웃바운드 전용 관리

현장 로봇은 대부분 고객사 네트워크의 **NAT/방화벽 뒤**에 있어서, 본사에서 로봇으로 **직접 접속할 수 없는** 경우가 많습니다. 그래서 실제 로봇 회사들은 이렇게 설계합니다.

```
 ┌─────────── 고객사 네트워크 ───────────┐                ┌──── 본사/클라우드 ────┐
 │  로봇 ──(나가는 연결: VPN/MQTT/WSS)────┼──────────────▶│ 플릿 관리 서버        │
 │   UFW: incoming 거의 전부 deny         │                │ VPN 게이트웨이         │
 └────────────────────────────────────────┘                │   ▲ 엔지니어는 여기로  │
                                                            └───┴───────────────────┘
```

- 로봇이 **먼저 밖으로** VPN(WireGuard 등) 터널을 연다 → 엔지니어는 VPN 안에서만 로봇에 SSH.
- 고객 Wi-Fi 쪽에서는 SSH 포트가 **아예 보이지 않는다.**

UFW 로 표현하면:

```bash
sudo ufw allow in on wg0 to any port 20022 proto tcp     # VPN 인터페이스로 들어온 SSH 만
sudo ufw allow from 10.20.0.0/16 to any port 15034 proto tcp   # 관제망에서만 앱 포트
# (Anywhere 로 열었던 미션 규칙은 삭제)
```

> ⚠️ SSH 를 VPN 에만 묶으면 **VPN 이 죽는 순간 원격 접근 수단이 사라집니다.** 반드시 OOB(셀룰러 관리 채널, 현장 절차)를 함께 설계합니다.

## 4. 📖 나가는 트래픽 제한 (Egress Filtering)

미션은 `default allow outgoing` 입니다. 하지만 로봇이 침해되면 공격자는 **밖으로** 데이터를 빼내거나 명령 서버(C2)에 접속합니다. 로봇이 연결할 곳은 정해져 있으므로(플릿 서버, NTP, DNS, 업데이트 미러) 나가는 것도 제한할 수 있습니다.

```bash
# 개념 예시 — 순서를 틀리면 즉시 통신이 끊기므로 dead man's switch 필수
sudo ufw default deny outgoing
sudo ufw allow out 53                       # DNS
sudo ufw allow out 123/udp                  # NTP
sudo ufw allow out to <플릿서버IP> port 443 proto tcp
sudo ufw allow out to <업데이트미러> port 443 proto tcp
```

실무 난이도가 높아(클라우드 IP 변경, CDN 등) 프록시 경유나 DNS 기반 정책을 함께 쓰는 경우가 많습니다.

## 5. 📖 UFW 가 "active" 인데도 뚫리는 경우

**Docker** — `docker run -p 8080:80` 으로 공개한 포트는 Docker 가 iptables `DOCKER` 체인에 직접 규칙을 넣기 때문에 **UFW 규칙보다 먼저 처리되어 허용**됩니다.

대응:
- 외부에 열 필요가 없으면 `-p 127.0.0.1:8080:80` 처럼 **루프백에만 바인드**
- 또는 Docker 가 제공하는 `DOCKER-USER` 체인에 차단 규칙 추가
- 그리고 항상 **외부에서 실측**(`nc`, `nmap`)으로 확인 (02장 2-7)

**ROS 2 (DDS)** — ROS 2 노드 탐색은 UDP 멀티캐스트/유니캐스트 7400번대 포트를 씁니다.
- Default Deny 를 켜면 로봇 내부 PC 간 통신이 끊김 → **내부 인터페이스에만** 허용 (`ufw allow in on eth1 proto udp to any port 7400:7600`)
- 외부 네트워크로 ROS 그래프가 새어나가지 않도록 `ROS_DOMAIN_ID` 분리, 로컬 전용 설정(배포판에 따라 `ROS_LOCALHOST_ONLY` 또는 `ROS_AUTOMATIC_DISCOVERY_RANGE`) 사용

## 6. 📖 원격 변경의 표준 절차 (Runbook)

로봇 플릿에 SSH/방화벽 변경을 배포할 때의 체크리스트입니다.

1. **사전**: 변경 내용 리뷰, 스테이징 로봇에서 검증, 롤백 절차 문서화
2. **안전장치**: dead man's switch(`at now + 5 minutes` 로 자동 원복) 또는 설정 관리 도구의 자동 롤백
3. **순서**: 새 경로 허용 → 설정 변경 → 문법 검사(`sshd -t`, `visudo -c`) → 재시작 → **새 세션으로 검증** → 옛 경로 제거
4. **카나리 배포**: 1대 → 5% → 25% → 100%, 단계마다 헬스 지표 확인
5. **사후**: 전 대수 실측 감사(외부 포트 스캔), 변경 기록 남기기

이 미션에서 한 "콘솔 창 열어두기 → 터미널 B 로 새 접속 검증" 이 이 절차의 축소판입니다.
