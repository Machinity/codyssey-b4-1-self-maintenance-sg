# 03. 계정과 그룹 — 역할 기반 접근 제어(RBAC)

## 이 장의 목표

| 미션 요구사항 | 확인 방법 |
|---|---|
| 계정 `agent-admin`, `agent-dev`, `agent-test` 생성 | `id agent-admin` 등 |
| 그룹 `agent-common` = admin, dev, test | `getent group agent-common` |
| 그룹 `agent-core` = admin, dev | `getent group agent-core` |

그리고 04장과 함께 다음을 **설명할 수 있어야** 합니다.
> 역할 기반 계정/그룹으로 "공유 디렉토리"와 "보안 디렉토리"를 분리하는 이유는?

---

## 1. 개념

### 1-1. 리눅스가 "누구"를 식별하는 방법

커널은 이름이 아니라 **숫자**로 사용자를 구분합니다.

| 파일 | 내용 | 예시 |
|---|---|---|
| `/etc/passwd` | 사용자 이름 ↔ **UID**, 기본 그룹 GID, 홈, 셸 | `agent-dev:x:1002:1002::/home/agent-dev:/bin/bash` |
| `/etc/group` | 그룹 이름 ↔ **GID**, 보조 그룹 멤버 | `agent-core:x:1005:agent-admin,agent-dev` |
| `/etc/shadow` | 비밀번호 해시 (root 만 읽기) | `agent-dev:!:...` (`!` = 잠김) |

- **기본 그룹(primary)**: 사용자가 만든 파일의 기본 그룹. Ubuntu는 사용자와 **같은 이름의 개인 그룹**을 자동으로 만듭니다(User Private Group).
- **보조 그룹(supplementary)**: 추가로 소속된 그룹. 권한 검사 시 기본 + 보조 그룹을 모두 봅니다.

### 1-2. 왜 "역할" 단위로 나누나 — 최소 권한 원칙

```
                agent-common (공유)          agent-core (핵심)
agent-admin          ●                            ●        운영/관리, cron 실행자
agent-dev            ●                            ●        개발/운영, monitor.sh 작성자
agent-test           ●                            ✗        QA/테스트
```

- 사람마다 권한을 따로 주면(ACL을 사람 이름으로 나열) 인원이 늘수록 관리가 불가능해집니다.
- **권한은 그룹에 주고, 사람은 그룹에 넣는다.** 입사/퇴사/역할 변경 시 그룹 멤버십만 바꾸면 됩니다.
- QA(`agent-test`)는 업로드 파일은 다뤄야 하지만 **API 키·운영 로그를 볼 이유가 없습니다.** 필요 없는 권한은 사고의 반경(blast radius)만 키웁니다.

### 1-3. `useradd` vs `adduser`

| 명령 | 특징 | 이 가이드 |
|---|---|---|
| `useradd` | 저수준, 옵션을 명시해야 함, 비대화형 → **스크립트/자동화에 적합** | ✅ 사용 |
| `adduser` | Debian 계열의 대화형 래퍼 | 수동 작업용 |

현장에서는 수백 대의 로봇에 같은 계정을 만들어야 하므로 비대화형(`useradd`)이 기본입니다.

## 2. 실습

### 2-1. 그룹 생성

```bash
ops@vm$ sudo groupadd agent-common
ops@vm$ sudo groupadd agent-core
ops@vm$ getent group agent-common agent-core
# agent-common:x:1001:
# agent-core:x:1002:
```

### 2-2. 계정 생성

```bash
ops@vm$ sudo useradd -m -s /bin/bash -c "Agent Ops Admin (cron runner)" agent-admin
ops@vm$ sudo useradd -m -s /bin/bash -c "Agent Developer (monitor.sh author)" agent-dev
ops@vm$ sudo useradd -m -s /bin/bash -c "Agent QA Tester" agent-test
```

| 옵션 | 의미 |
|---|---|
| `-m` | 홈 디렉토리 생성 (`/home/<이름>`) |
| `-s /bin/bash` | 로그인 셸 (생략 시 `/bin/sh`) |
| `-c` | 설명(GECOS). **누가 어떤 역할인지** 계정 목록만 봐도 알 수 있게 |

### 2-3. 그룹에 추가

```bash
ops@vm$ sudo usermod -aG agent-common,agent-core agent-admin
ops@vm$ sudo usermod -aG agent-common,agent-core agent-dev
ops@vm$ sudo usermod -aG agent-common            agent-test
```

> ⚠️ **`-a`(append) 를 빼먹으면** 기존 보조 그룹이 전부 지워지고 지정한 그룹으로 **교체**됩니다. `ops` 계정에 이 실수를 하면 `sudo` 그룹에서 빠져 관리자 권한을 잃습니다. 현업에서 실제로 자주 나는 사고입니다.

### 2-4. 검증

```bash
ops@vm$ id agent-admin
# uid=1001(agent-admin) gid=1003(agent-admin) groups=1003(agent-admin),1001(agent-common),1002(agent-core)
ops@vm$ id agent-dev
# uid=1002(agent-dev) gid=1004(agent-dev) groups=1004(agent-dev),1001(agent-common),1002(agent-core)
ops@vm$ id agent-test
# uid=1003(agent-test) gid=1005(agent-test) groups=1005(agent-test),1001(agent-common)

ops@vm$ getent group agent-common agent-core
# agent-common:x:1001:agent-admin,agent-dev,agent-test
# agent-core:x:1002:agent-admin,agent-dev
```

(숫자는 환경마다 다를 수 있습니다.)

✅ 체크포인트: `agent-test` 의 groups 에 `agent-core` 가 **없다.**

### 2-5. 비밀번호 상태 확인 — 왜 비밀번호를 안 만드나

```bash
ops@vm$ sudo passwd -S agent-admin
# agent-admin L 09/23/2026 0 99999 7 -1       ← L = Locked
```

`useradd` 로 만든 계정은 비밀번호가 **잠긴 상태**입니다. 즉 **비밀번호로 SSH 로그인이 불가능**합니다. 이 미션에서는 관리자(`ops`)가 `sudo -iu` 로 전환해서 작업하므로 비밀번호가 필요 없습니다.

```bash
ops@vm$ sudo -iu agent-dev      # agent-dev 의 "로그인 셸"로 전환 (-i: 환경을 새로 로드)
agent-dev@vm$ whoami; id; pwd
agent-dev@vm$ exit
```

> 비밀번호를 꼭 만들어야 한다면 `sudo passwd agent-admin`. 다만 사람이 원격 접속해야 하는 계정이라면 비밀번호보다 **SSH 공개키**를 등록하는 것이 원칙입니다. ([F2](field/F2_원격접속과_네트워크.md))

### 2-6. 그룹 변경이 "언제" 적용되는가

그룹 멤버십은 **로그인(세션 시작) 시점**에 프로세스에 복사됩니다. 이미 떠 있는 셸/프로세스에는 반영되지 않습니다.

```bash
# 이미 agent-dev 로 로그인해 있던 셸이라면 → exit 후 다시 sudo -iu agent-dev
# 실행 중인 앱/서비스라면 → 재시작해야 새 그룹 권한을 얻는다
```

"그룹에 넣었는데 Permission denied" 의 90%는 이 문제입니다.

### 2-7. sudo 권한은 주지 않는다

```bash
ops@vm$ sudo -l -U agent-admin
# User agent-admin is not allowed to run sudo on robot-01.
```

agent-* 계정은 **sudo 그룹에 넣지 않습니다.** monitor.sh 가 방화벽 상태를 조회하려면 root 권한이 필요한데, 이것은 06장에서 **딱 그 명령 하나만** 허용하는 방식으로 해결합니다.

## 🤖 현장 노트 — 로봇의 계정 관리

1. **사람 계정과 서비스 계정을 분리** — 미션의 `agent-admin` 은 "사람(운영자)"이면서 "앱 실행 주체"를 겸합니다. 현장에서는 보통 앱 전용 계정을 따로 둡니다.
   ```bash
   sudo useradd -r -s /usr/sbin/nologin -d /nonexistent agent-svc   # 시스템 계정, 로그인 불가
   ```
   앱이 탈취되어도 공격자는 대화형 셸을 얻기 어렵고, 사람 계정의 SSH 키·셸 기록에 접근할 수 없습니다.
2. **공용 계정 금지** — 엔지니어 여러 명이 `agent-admin` 하나를 같이 쓰면 "누가" 했는지 알 수 없습니다. 개인 계정 + 역할 그룹 + `sudo` 로그가 기본입니다.
   ```bash
   sudo journalctl _COMM=sudo --since today     # 누가 언제 무엇을 sudo 로 했나
   last -n 10                                   # 최근 로그인 기록
   ```
3. **플릿(수백 대) 규모** — 로봇마다 손으로 계정을 만들지 않습니다. Ansible 같은 구성 관리 도구나 이미지 빌드 단계에서 **코드로** 만들고, 사람 계정은 중앙 인증(LDAP/SSSD, 또는 SSH 인증서)으로 관리해 퇴사자 계정을 한 번에 회수합니다.
4. **UID/GID 고정** — 여러 로봇의 백업 파일이나 NFS 를 다룰 때 UID가 로봇마다 다르면 소유권이 뒤섞입니다. 이미지에서 `useradd -u 2001` 처럼 **고정 UID**를 쓰는 경우가 많습니다.
