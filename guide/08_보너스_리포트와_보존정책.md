## Part 1. report.sh — 로그를 숫자로 바꾸기

### 1-1. 개념: 로그 분석 파이프라인

```
monitor.log ──▶ ① 필터 (형식 맞는 줄 + 시간 구간) ──▶ ② 파싱 (키:값 → 숫자) ──▶ ③ 집계 (합·최대·최소·개수) ──▶ 출력
```

- 06장에서 로그 형식을 `[시각] 키:값` 으로 **고정**해 두었기 때문에 이 파이프라인이 단순해집니다. 로그 형식 설계는 **나중에 읽을 사람(=분석 스크립트)** 을 위한 것입니다.
- `[ERROR]` 줄처럼 형식이 다른 줄은 **정규식으로 걸러냅니다.** 분석 스크립트는 "예상치 못한 줄"에 깨지면 안 됩니다.
- 시각 형식 `YYYY-MM-DD HH:MM:SS` 는 **문자열 비교 = 시간 비교**가 성립합니다. `"2026-09-23 14:00:00" < "2026-09-23 14:05:00"` → 날짜 변환 없이 구간 필터가 가능합니다.

### 1-2. awk 핵심 문법 (report.sh 에서 쓰는 것만)

```awk
패턴 { 동작 }                 # 패턴에 맞는 줄마다 동작 실행
$1, $2, ..., NF               # 공백으로 나눈 필드, 필드 개수
substr($0, 2, 19)             # 줄 전체($0)의 2번째 글자부터 19글자 → 시각
split("CPU:25.3%", kv, ":")   # kv[1]="CPU", kv[2]="25.3%"
END { ... }                   # 모든 줄을 읽은 뒤 1번 실행 → 결과 출력
-v 변수=값                     # 셸 값을 awk 로 전달
```

### 1-4. 검증 — 다른 방법으로 계산한 값과 비교

```bash
# 샘플 수: 측정 줄 개수와 같은가
ops@vm$ sudo grep -c 'PID:[0-9]* CPU:' /var/log/agent-app/monitor.log

# CPU 최대값: 정렬로 구한 값과 같은가
ops@vm$ sudo grep -o 'CPU:[0-9.]*' /var/log/agent-app/monitor.log | cut -d: -f2 | sort -n | tail -n1
```

> 🤖 **현장 노트**: 로봇 한 대의 리포트는 "이 로봇이 이상한가?"에 답하고, 플릿 전체 리포트는 "**이 로봇만** 이상한가, 아니면 **소프트웨어 버전 전체**가 이상한가?"에 답합니다. 현장에서는 이런 집계를 중앙 서버(Prometheus/Grafana 등)에서 하고, 로봇 위의 스크립트는 네트워크가 끊겼을 때 현장 기술자가 쓰는 **오프라인 진단 도구**로 남겨둡니다.

## Part 2. log_retention.sh — 시간 기반 보존 정책

### 2-1. 개념

**크기 기반 회전(06장)** 과 **시간 기반 보존(이 장)** 은 목적이 다릅니다.

| | 크기 기반 (monitor.sh) | 시간 기반 (log_retention.sh) |
|---|---|---|
| 기준 | 파일이 10MB 넘으면 | 파일이 N일 지나면 |
| 막는 것 | 파일 하나의 폭주 | 오래된 데이터의 누적 |
| 대상 | monitor.log | agent-app 디렉토리의 모든 로그 (agent_app.log 계열 포함) |

**`find -mtime` 의 함정** — `-mtime +7` 은 "7일 이상"이 아니라 **"8일 이상"** 입니다. find 는 경과 시간을 24시간 단위로 **내림**한 뒤 **초과(>)** 를 비교하기 때문입니다.

| 파일 나이 | 내림한 값 | `-mtime +6` | `-mtime +7` |
|---|---|---|---|
| 6일 23시간 | 6 | ✗ | ✗ |
| 7일 1시간 | 7 | ✅ | ✗ |
| 8일 1시간 | 8 | ✅ | ✅ |

→ "7일 이상 경과" 는 `-mtime +6`, "30일 이상 경과" 는 `-mtime +29`.

**안전한 압축 순서** — `압축본 생성 → 성공 확인 → 원본 삭제`. 압축 도중 디스크가 가득 차거나 실패하면 원본이 남아 있어야 합니다. (`gzip 원본` 은 성공 시 원본을 지우지만, 결과물 위치를 제어하기 어렵습니다.)

**예외 처리 원칙** — 보존 작업이 실패해도 **서비스에 영향이 없어야** 합니다. 디렉토리가 없거나 권한이 없으면 **경고만 남기고 정상 종료(0)** 합니다. 반대로 "무엇을 지울지 확신할 수 없으면 아무것도 지우지 않는다"가 삭제 작업의 철칙입니다. → `-n`(dry-run) 옵션.

### 2-2. 아카이브 디렉토리 준비 (ops)

`/var/log` 아래는 root 만 쓸 수 있으므로 관리자가 먼저 만들어 둡니다.

```bash
ops@vm$ sudo mkdir -p /var/log/monitor/agent-app/archive
ops@vm$ sudo chown agent-admin:agent-core /var/log/monitor/agent-app/archive
ops@vm$ sudo chmod 2770 /var/log/monitor/agent-app/archive
ops@vm$ sudo setfacl -d -m u::rwx,g::rwx,o::--- /var/log/monitor/agent-app/archive
ops@vm$ ls -ld /var/log/monitor/agent-app/archive
# drwxrws---+ 2 agent-admin agent-core ... archive
```

> 아카이브도 운영 로그이므로 04장의 로그 디렉토리와 **같은 보안 수준**(agent-core ONLY)으로 둡니다.

### 2-3. 설치

```bash
ops@vm$ sudo install -o agent-dev -g agent-core -m 750 $REPO/scripts/log_retention.sh $AH/bin/log_retention.sh
```

### 2-4. 테스트 데이터 만들기 — `touch -d` 로 시간 여행

실제로 7일, 30일을 기다릴 수는 없으므로 파일의 수정 시각(mtime)을 과거로 바꿉니다.

```bash
ops@vm$ sudo -u agent-admin bash -c '
  cd /var/log/agent-app
  printf "old log line\n"    > test_old.log;    touch -d "8 days ago" test_old.log      # 압축 대상
  printf "edge log line\n"   > test_edge.log;   touch -d "7 days ago 1 hour ago" test_edge.log  # 7일 1시간: 대상
  printf "recent log line\n" > test_recent.log; touch -d "3 days ago" test_recent.log   # 대상 아님
  printf "rotated line\n"    > test_rot.log.1;  touch -d "10 days ago" test_rot.log.1   # 회전 파일도 대상
  cd /var/log/monitor/agent-app/archive
  printf "x" | gzip > very_old.log.20260801.gz; touch -d "31 days ago" very_old.log.20260801.gz  # 삭제 대상
  printf "y" | gzip > keep.log.20260910.gz;     touch -d "13 days ago" keep.log.20260910.gz     # 유지
'
ops@vm$ sudo ls -l --time-style=+%F /var/log/agent-app/ /var/log/monitor/agent-app/archive/
```

### 2-5. dry-run → 실제 실행

```bash
# 1) 무엇을 할지 먼저 본다 (아무것도 바뀌지 않음)
ops@vm$ sudo -u agent-admin $AH/bin/log_retention.sh -n
# [INFO] DRY-RUN 모드: 파일을 변경하지 않습니다.
#   (dry-run) gzip /var/log/agent-app/test_old.log -> /var/log/monitor/agent-app/archive/test_old.log.20260915.gz
#   (dry-run) gzip /var/log/agent-app/test_edge.log -> ...
#   (dry-run) gzip /var/log/agent-app/test_rot.log.1 -> ...
#   (dry-run) rm /var/log/monitor/agent-app/archive/very_old.log.20260801.gz
# [SUMMARY] compressed=3 failed=0 deleted=1

# 2) 기대와 같으면 실제 실행
ops@vm$ sudo -u agent-admin $AH/bin/log_retention.sh
ops@vm$ sudo ls -l /var/log/agent-app/ /var/log/monitor/agent-app/archive/
```

✅ 체크포인트:
- `test_old.log`, `test_edge.log`, `test_rot.log.1` → 사라지고 archive 에 `.gz` 로 존재
- `test_recent.log`, `monitor.log`, `agent_app.log` → 그대로 (최근 파일)
- `very_old...gz` → 삭제, `keep...gz` → 유지

```bash
# 압축본 내용 확인
ops@vm$ sudo bash -c 'zcat /var/log/monitor/agent-app/archive/test_old.log.*.gz'   # * 는 root 셸 안에서 펼쳐야 함
# old log line
```

📸 스크린샷: dry-run 출력, 실행 전/후 `ls`.

### 2-6. 예외 처리 테스트

```bash
# ① 대상 0개 (방금 다 처리했으므로)
ops@vm$ sudo -u agent-admin $AH/bin/log_retention.sh
# [INFO] 압축 대상 없음 ... / [INFO] 삭제 대상 없음 ...

# ② 원본 디렉토리 없음
ops@vm$ sudo -u agent-admin env AGENT_LOG_DIR=/var/log/nope $AH/bin/log_retention.sh; echo "exit=$?"
# [WARNING] 원본 디렉토리가 없습니다: /var/log/nope  → 작업 없이 종료
# exit=0

# ③ 권한 부족 (agent-core 가 아닌 사용자) — 스크립트 실행 자체가 막힘
ops@vm$ sudo -u agent-test $AH/bin/log_retention.sh
# Permission denied
#    스크립트 권한을 우회해 직접 bash 로 돌려도 디렉토리 권한 검사에서 안전 종료되는지:
ops@vm$ sudo cp $AH/bin/log_retention.sh /tmp/lr.sh && sudo chmod 755 /tmp/lr.sh
ops@vm$ sudo -u agent-test bash /tmp/lr.sh; echo "exit=$?"
# [WARNING] 원본 디렉토리 권한 부족: /var/log/agent-app (user: agent-test)  → 작업 없이 종료
# exit=0
ops@vm$ sudo rm /tmp/lr.sh

# 테스트 파일 정리
#   (ops 는 이 디렉토리를 읽을 수 없어 * 가 펼쳐지지 않으므로, agent-admin 의 셸 안에서 펼친다)
ops@vm$ sudo -u agent-admin bash -c 'rm -f /var/log/agent-app/test_recent.log /var/log/monitor/agent-app/archive/{test_,keep.}*'
```

### 2-8. (비교 학습) logrotate 로 같은 일을 한다면

Ubuntu 에는 로그 회전 표준 도구 `logrotate` 가 있습니다 (`/etc/logrotate.d/` 의 rsyslog, apt 등이 이미 사용 중).

```bash
ops@vm$ cat $REPO/config/logrotate/agent-app      # 크기 회전 설정 예시 (주석 참고)
ops@vm$ sudo logrotate -d $REPO/config/logrotate/agent-app 2>&1 | head -n 20   # dry-run 으로 동작만 확인
```

| | 직접 구현(이 미션) | logrotate |
|---|---|---|
| 장점 | 동작을 완전히 이해·통제, 즉시 테스트 | 검증된 표준, `compress`/`maxage`/`dateext` 등 옵션 풍부 |
| 단점 | 엣지 케이스를 직접 처리해야 함 | 하루 1회 실행(타이머) 기준, `su` 등 권한 설정 함정 |

현업에서는 대부분 **logrotate(또는 journald 설정)** 를 씁니다. 직접 구현해 본 경험은 logrotate 설정을 **정확히 읽고 문제를 진단하는 능력**이 됩니다. (단, monitor.sh 내장 회전과 logrotate 를 동시에 켜지 마세요.)
