### 1-4. 왜?

SSH 포트 변경과 root 원격 로그인 차단은 서버 노출면을 줄이는 기본 보안 설정이다. 포트 변경은 22번을 노리는 자동화된 스캔과 로그 노이즈를 줄여 주지만, 포트 스캔 한 번이면 20022도 드러나므로 은폐에 불과하다. 따라서 방화벽, 키 인증, root 차단과 겹쳐 쓰는 심층 방어의 일부로만 의미가 있다. root 로그인을 막으면 모든 시스템에 존재하는 계정명을 노린 대입 공격이 차단되고, 개별 계정과 sudo를 통해 누가 어떤 관리자 명령을 실행했는지 로그에 남는다. 설정은 메인 `sshd_config`를 직접 고치지 않고 `/etc/ssh/sshd_config.d/10-agent-hardening.conf` drop-in 파일로 분리했다. 패키지 업데이트와 충돌하지 않고, 문제가 생기면 파일 하나만 삭제해 즉시 되돌릴 수 있으며, 변경 내역이 한 파일에 모여 감사하기 쉽기 때문이다.

1. 포트를 20022로 바꾸는 것만으로 안전하다고 할 수 없는 이유는?
   - 포트 변경은 "은폐를 통한 보안(security through obscurity)"이다. 22번을 노리는 자동화된 스캔과 로그 노이즈를 줄여 주지만 인증을 강화하지는 않는다.
   - 포트 스캔(`nmap` 등) 한 번이면 20022가 열려 있다는 사실과 SSH 서비스임이 바로 드러난다. 이사 가서 호수만 바꾸고 문에 잠금장치가 없는 것과 같다.
   - 실제 잠금장치는 방화벽(필요 포트만 허용), 공개키 인증, root 로그인 차단이다. 포트 변경은 이것들과 겹쳐 쓰는 심층 방어(defense in depth)의 한 겹으로만 의미가 있다.

2. root 원격 로그인을 막으면 "책임 추적성"이 왜 좋아지는가?
   - root로 직접 접속하면 공유 비밀번호나 공유 키 하나로 여러 사람이 들어올 수 있어, 누가 관리자 권한으로 무엇을 바꿨는지 로그만으로는 구분할 수 없다.
   - 개별 계정으로 접속한 뒤 `sudo`를 쓰면 `/var/log/auth.log`와 `journalctl`에 누가, 언제, 어떤 명령을 실행했는지 남는다.
   - 부가 이점으로, `root`는 모든 리눅스에 존재하는 계정명이라 공격자가 사용자명을 추측할 필요 없이 비밀번호만 대입하면 된다. root 로그인을 막으면 이 공격이 차단된다.

3. `sshd` 를 재시작해도 기존 SSH 세션이 끊기지 않는 이유는?
   - sshd는 접속마다 자식 프로세스를 fork해 그 세션을 맡기고, 재시작으로 교체되는 것은 접속을 기다리는 메인(부모) 프로세스뿐이다.
   - systemd는 보통 재시작 시 서비스에 속한 모든 프로세스를 종료하지만, Ubuntu의 `ssh.service`는 `KillMode=process`로 설정되어 메인 프로세스만 종료된다. (`systemctl cat ssh | grep KillMode`로 확인)
   - 기존 세션은 옛 설정으로 계속 살아 있으므로, 새 세션으로 20022 접속을 검증한 뒤에 기존 세션을 닫는다. 설정 실수로 새 접속이 막혀도 기존 세션으로 복구할 수 있다.

4. 파일을 grep 하는 것보다 `sshd -T` 로 검증하는 것이 나은 이유는?
   - `sshd -T`는 설정 파일을 다시 읽어 `Include`, "처음 나온 값 우선(first match wins)" 규칙, 기본값까지 합친 **최종 적용값**을 보여 준다.
   - `grep`은 주석 줄과 다른 파일에 덮어쓰인 줄까지 그대로 보여 주므로 실제로 적용될 값을 알 수 없다.
   - 다만 `sshd -T`는 디스크 설정의 계산 결과이지 실행 중인 데몬의 상태가 아니다. 재시작 전이면 실행 중인 sshd는 옛 값을 쓰고 있을 수 있어서, `ss -tulnp | grep sshd`로 실제 LISTEN 상태를 함께 확인한다.

5. 메인 파일에 `Port 22` 가 살아 있으면 어떻게 되는가?
   - `Port`는 대부분의 키워드(처음 나온 값 우선)와 달리 값이 **누적**되어, sshd가 22와 20022를 **둘 다 LISTEN**한다. (`sshd -T`에 port 두 줄, `ss`에 LISTEN 두 줄)
   - "20022로 변경"이라는 요구에 어긋나고, 방화벽이 꺼지거나 규칙이 어긋나는 순간 불필요한 입구가 된다.
   - 메인 파일의 `Port 22`를 주석 처리(`#Port 22`)하고 sshd를 재시작해 해결한 뒤, `ss`에 20022만 남았는지 확인한다.

## 2. 방화벽(UFW)

### 2-1. 수행 명령

```bash
ops@robot-01$ sudo ss -tulnp | grep sshd  

ops@robot-01$ sudo ufw status verbose

ops@robot-01$ sudo ufw --force reset

ops@robot-01:~$ sudo ufw default deny incoming

ops@robot-01:~$ sudo ufw default allow outgoing

ops@robot-01:~$ sudo ufw default deny routed

ops@robot-01:~$ sudo ufw allow 20022/tcp comment 'SSH (custom port)'

ops@robot-01:~$ sudo ufw allow 15034/tcp comment 'agent-app'

ops@robot-01:~$ sudo ufw show added

ops@robot-01:~$ sudo ufw enable

ops@robot-01:~$ sudo ufw status verbose

ops@robot-01:~$ sudo ufw status numbered

ops@robot-01:~$ systemctl is-enabled ufw

ops@robot-01:~$ grep ENABLED /etc/ufw/ufw.conf

mac$ nc -vz -w 3 <VM_IP> 20022

mac$ nc -vz -w 3 <VM_IP> 15034

mac$ nc -vz -w 3 <VM_IP> 22

ops@robot-01:~$ python3 -m http.server 8080  

mac$ nc -vz -w 3 <VM_IP> 8080 

ops@vm$ sudo ufw logging low   

ops@robot-01:~$ sudo journalctl -k --since "10 min ago" | grep 'UFW BLOCK' | tail -n 3
```

### 2-2. 확인 결과

```
ops@robot-01:~$ sudo ufw status verbose
Status: active
Logging: on (low)
Default: deny (incoming), allow (outgoing), disabled (routed)
New profiles: skip

To                         Action      From
--                         ------      ----
20022/tcp                  ALLOW IN    Anywhere                   # SSH (custom port)
15034/tcp                  ALLOW IN    Anywhere                   # agent-app
20022/tcp (v6)             ALLOW IN    Anywhere (v6)              # SSH (custom port)
15034/tcp (v6)             ALLOW IN    Anywhere (v6)              # agent-app
```

| 외부 테스트 (`nc -vz`) | 결과 |
|---|---|
| 20022 | Connection to <VM_IP> port 20022 [tcp/*] succeeded! |
| 15034 (앱 실행 중) | nc: connectx to <VM_IP> port 15034 (tcp) failed: Connection refused |
| 22 | 응답 없음|

### 2-3. 왜?

방화벽은 incoming을 기본 차단(deny)하고 SSH(20022/tcp)와 앱(15034/tcp)만 허용하는 화이트리스트 방식으로 구성했다. 허용 목록 방식은 목록에 없는 새 서비스나 실수로 열린 포트가 자동으로 차단되므로, 막을 대상을 일일이 나열하는 방식보다 안전하다. 나가는 연결(outgoing)은 허용하고 그 응답은 conntrack이 ESTABLISHED 상태로 추적해 자동 허용하므로 `apt update` 같은 외부 통신은 유지된다. 다만 `ufw status`는 설정 값일 뿐이라 Docker처럼 ufw를 우회하는 경우를 잡지 못하므로, 외부에서 `nc`/`nmap`으로 실제 응답을 확인하는 실측까지 해야 검증이 끝난다.

1. `default deny incoming` 인데도 VM에서 `apt update` 가 되는 이유는?
   - 기본 정책이 incoming은 deny, outgoing은 allow이기 때문이다. VM이 먼저 밖으로 보낸 요청은 막히지 않는다. 그 응답 패킷은 커널 netfilter의 conntrack이 ESTABLISHED/RELATED 상태로 인식하고, ufw가 설정해 둔 규칙(`before.rules`)이 이를 자동 허용한다. 즉, deny incoming은 **외부에서 먼저 시작한 새 연결(NEW)**에만 적용된다.
  
2. 외부에서 봤을 때 "Connection refused" 와 "timeout" 은 각각 무엇을 의미하는가?
   - refused: 패킷이 VM까지 도달했다는 뜻이다(방화벽이 통과시킴). 해당 포트에서 LISTEN하는 프로세스가 없어서 커널이 RST로 거부 응답을 보낸 것이다. 앱 실행 전 15034가 refused인 것은 정상이다.
   - timeout: 방화벽이 패킷을 DROP해서 아무 응답이 오지 않은 것이다. ufw의 deny는 REJECT가 아니라 DROP이라 공격자에게 포트 존재 여부조차 알려주지 않는다. 단, 호스트 다운이나 경로 문제도 같은 증상이므로 다른 포트의 응답 여부와 함께 판단한다.

3. `ufw allow 15034` 와 `ufw allow 15034/tcp` 의 차이는?
   - 프로토콜을 생략하면 tcp와 udp 규칙이 모두 생성된다(v4/v6 각각). `/tcp`는 TCP만 허용한다. 앱은 TCP만 쓰므로 UDP까지 열 이유가 없다. 필요한 것만 여는 최소 권한 원칙에 따라 `/tcp`를 명시한다. `ufw status`에서 `15034`와 `15034/tcp`로 구분되어 보인다.

4. `ufw status` 가 active 이면 모든 포트가 안전하다고 말할 수 없는 사례를 하나 드시오.
   - Docker: `docker run -p 8080:80`으로 publish한 포트는 Docker가 iptables에 ufw보다 먼저 평가되는 규칙(DNAT/FORWARD 경로)을 넣기 때문에, `ufw deny`를 해도 외부에서 접근된다. `ufw status`에는 8080이 허용된 흔적조차 없어서 안전하다고 오판하기 쉽다.
   - 대응: 바인딩 주소를 제한(`-p 127.0.0.1:8080:80`)하거나 DOCKER-USER 체인에서 제어하고, 반드시 외부에서 실측한다.
   - 그 외 예: `/etc/default/ufw`에서 `IPV6=no`면 IPv6 포트는 ufw 관리 밖이라 열려 있을 수 있다.

5. 방화벽 규칙을 검증하는 두 가지 방법(설정 확인 / 실측)을 설명하시오.
   - 설정 확인(정적): 서버 안에서 `ufw status verbose`, `ufw status numbered`로 의도한 규칙과 기본 정책을 확인한다.
   - 실측(동적): 서버 **외부**에서 실제 패킷을 보내 응답을 본다. `nc -vz -w 3 <VM_IP> 15034`, `nmap -p 22,20022,15034 <VM_IP>`. nmap의 open / closed / filtered는 각각 succeeded / refused / timeout에 대응한다. VM 안에서 localhost로 테스트하면 loopback이라 방화벽을 거치지 않아 의미가 없다.
   - 둘 다 필요한 이유: 설정 확인은 "의도한 정책"이고 실측은 "실제 동작"이다. Docker 우회나 IPv6 설정처럼 둘이 어긋나는 경우는 실측으로만 발견된다.

### 4-4. 왜?

공유 디렉토리(`upload_files`)에는 admin·dev·test가 함께 쓰는 작업 데이터가, 보안 디렉토리(`api_keys`, `/var/log/agent-app`)에는 API 키와 운영 기록이 담긴다. 데이터의 민감도가 다르면 권한 경계도 나눠야 하며, 한 곳에 섞으면 업로드만 필요한 QA 계정도 키와 로그에 접근하게 된다. 공유 디렉토리가 실제로 공유되도록 setgid로 새 파일의 그룹을 디렉토리의 그룹에 고정했고, default ACL로 사용자별 umask와 무관하게 그룹 읽기/쓰기가 상속되게 했다. 홈 디렉토리는 755로 열지 않고 ACL `g:agent-common:--x`로 필요한 그룹에게 통과 권한만 부여했다.

1. 디렉토리의 `r` 과 `x` 는 각각 무엇을 허용하는가? `x` 만 있으면 무엇이 가능한가?
   - `r`: 디렉토리 안의 **이름 목록**을 읽는다(`ls`).
   - `x`: 디렉토리를 **통과(진입)**한다(`cd`, 그리고 하위 경로 접근). 하위 경로에 접근하려면 경로상의 모든 디렉토리에 `x`가 필요하다.
   - `x`만 있으면 목록은 볼 수 없지만, **이름을 알고 있는 하위 항목**에는 접근할 수 있다(항목 자체의 권한이 허용하는 범위에서). 그래서 `g:agent-common:--x`는 "홈 안을 구경하게 하지 않고 그 아래 경로로 가는 길만 열어 주는" 설정이다.
   - 참고로 파일의 생성·삭제·이름 변경은 디렉토리의 `w`(와 `x`)에서 나오며, 파일 삭제 권한은 파일이 아니라 디렉토리의 `w`에 달려 있다.

2. setgid 디렉토리가 없으면 공유 디렉토리에서 어떤 문제가 생기는가?
   - 새 파일의 그룹이 **만든 사람의 기본 그룹**이 된다. 예를 들어 agent-dev가 `upload_files`에 만든 파일의 그룹은 `agent-dev`(개인 그룹)가 되어, agent-test는 그 파일을 읽거나 수정할 수 없다. 공유 디렉토리가 공유되지 않는 것이다.
   - 디렉토리에 setgid(`2770`의 `2`)를 주면 새 파일과 하위 디렉토리가 **디렉토리의 그룹(agent-common)**을 상속하고, 하위 디렉토리에도 setgid가 전파된다.

3. umask 에 의존하지 않고 default ACL 을 쓰는 이유는?
   - 새 파일의 권한은 `666 & ~umask`인데, umask는 사용자와 접속 방식(SSH, cron, sudo)마다 다를 수 있다. 흔한 `022`면 파일이 `644`가 되어 그룹이 쓸 수 없고, 협업 규칙이 각 사용자의 환경 설정에 좌우된다.
   - 디렉토리에 default ACL(`d:g::rwx`)이 있으면 새 파일에 umask 대신 default ACL이 적용되어, 누가 어떤 umask로 만들든 그룹 읽기/쓰기가 보장된다. 정책을 사용자의 환경이 아니라 **디렉토리 자체**에 두는 것이다.
   - 실험으로 확인했다. `umask 077`로 만든 파일도 `-rw-rw----+`에 그룹이 agent-common으로 나왔다.

4. `/home/agent-admin` 을 `755` 로 여는 대신 ACL `g:agent-common:--x` 를 쓴 이유는?
   - `AGENT_HOME`이 `/home/agent-admin` 아래에 있는데 홈이 `750`이라, other에 해당하는 agent-dev와 agent-test는 경로를 통과조차 못 한다.
   - `755`로 열면 시스템의 **모든 사용자**가 홈의 목록까지 볼 수 있어 과잉 허용이고, `751`도 모든 사용자가 통과할 수 있다.
   - ACL을 쓰면 **agent-common 그룹에게만**, 필요한 최소 권한인 **통과(`--x`)만** 줄 수 있다. 목록 보기는 불가하고 other는 여전히 `---`이다. 필요한 대상에게 필요한 만큼만 주는 최소 권한 원칙이다.

5. API 키와 로그를 `agent-core` 로만 제한해야 하는 이유를 각각 설명하시오. (로그는 왜 "쓰기"까지 제한해야 하는가?)
   - API 키: 비밀 값이라 유출되면 외부 서비스를 도용당한다. 읽기를 막아야 하고, 쓰기까지 막아야 키를 바꿔치기해 앱을 오동작시키거나 공격자의 키로 교체하는 일을 막을 수 있다. 업무상 필요 없는 QA(agent-test)는 접근 대상에서 제외한다.
   - 로그(읽기 제한): 경로, IP, 오류 내용, 시스템 상태 같은 내부 구조가 담겨 공격자에게 정찰 정보가 된다.
   - 로그(쓰기 제한): 로그에 쓰거나 지울 수 있으면 침입이나 장애의 흔적을 **변조·삭제해 사고를 은폐**할 수 있다. 그러면 로그를 근거로 한 원인 분석과 책임 추적이 신뢰를 잃는다. 로그는 기록을 남기는 쪽(monitor.sh를 cron으로 돌리는 agent-admin, 작성자 agent-dev)과 확인하는 쪽의 권한이 통제되어야 증거로서 가치가 있다. 삭제 권한이 디렉토리의 `w`에서 나오므로 디렉토리를 `agent-core` 전용(`2770`, other `---`)으로 둔다.

증거: `evidence/04_dirs_acl.txt`
